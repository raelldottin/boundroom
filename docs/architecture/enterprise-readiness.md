# SPEC-009: Enterprise readiness

Status: **proposed** in the pull request that adds it. Merging that pull request, after a person's approving review, accepts the plan. Each delivery slice below is still its own pull request with its own approval. A slice marked *owner gate* needs a person's decision before an agent starts it.

## Problem

The owner wants Boundroom to be something an enterprise can adopt, audit and run, and to be on par with a mature open-source developer tool. This spec measures Boundroom against one such tool, finds the gaps, and orders the work to close them.

The reference is [headroom](https://github.com/headroomlabs-ai/headroom), read at its default branch on 2026-11-14 through the GitHub API. Nothing was cloned or run. Headroom is a context-compression library, proxy and MCP server: Apache-2.0, on PyPI and npm, with signed container images and a release roughly every week (v0.44.0 on 2026-11-10). It is not a supervisor like Boundroom, so the comparison is about practice, not features.

## What "enterprise-ready" means here

An enterprise can adopt Boundroom when it can answer yes to these questions:

1. **Can we trust what we install?** Releases are reproducible, signed or attested, and come with a bill of materials.
2. **Can we audit what it did?** Every supervised run leaves a record a reviewer can follow, and nothing changes what is released without a person's recorded approval.
3. **Can we control what leaves the machine?** Telemetry and every other network call are off unless the operator turns them on, and an offline switch can prove nothing leaves.
4. **Can we operate it?** Install, configuration, upgrade, observability, troubleshooting and support are documented, versioned and stable.
5. **Can we use it legally and safely?** The license fits the enterprise's policy, and security reports have a clear path.
6. **Is it ours, not someone else's?** Nothing in the product assumes one particular consumer.

## Where Boundroom already stands

Boundroom is ahead of headroom in some places. These stay as they are.

| Area | Boundroom today |
| --- | --- |
| Change control | Every change reaches `main` through a pull request with five required checks. A person other than the author approves every merge, release tag, spend, cutover and license change ([control map](../compliance/controls.md)). The agent acts as its own GitHub App identity. |
| Release source | A release is a tag on `main`, built by `release.yml`, which reruns the gate and publishes the archive and its `.sha256`. Only the owner's role can create tags. |
| Telemetry consent | Telemetry is off by default and can't be turned on by a repository. There is no vendor beacon and nothing is ever sent to Logfire's service ([SPEC-006](agent-telemetry.md)). Headroom, by contrast, sends an anonymous usage beacon by default. |
| Runner safety | A supervised Claude runner starts in the `bounded` profile: `dontAsk`, the slice's own allowlist, and a sandbox that fails closed ([SPEC-008](plugin-settings.md)). |
| Supply chain basics | Actions are pinned by commit, Dependabot covers actions and `uv`, dependency review and `pip-audit` run on every pull request, and dependencies are pinned exactly. |
| Vulnerability reporting | `SECURITY.md` uses GitHub private vulnerability reporting, with a 5-business-day acknowledgement. |

## Gaps

Each gap names the headroom practice it is measured against, and where in headroom it lives.

### 1. The product isn't generic yet (P0)

- **The runner prompt is one consumer's.** `automation/prompts/base.md` is titled "Owlory Supervised Slice Run" and tells every runner where Owlory's iOS layers live (`owlory_xcode/Owlory/Core/...`). Every consumer's runner gets those rules. The prompt must be generic, with consumer rules coming from the consumer's own files.
- **Consumer-specific code paths remain.** `Tools/boundroom-sync.sh` has an `allow_owlory_specific` flag and an `owlory_xcode/` deny rule, and `run_agent.sh` and the nested-run guard still read `OWLORY_*` names. SPEC-005 kept the old `REPO_AUTOMATION_*` names as aliases "no earlier than v0.4.0"; v0.4.0 has shipped.

### 2. Release integrity and supply chain (P0)

| Practice | Headroom | Boundroom |
| --- | --- | --- |
| Signed or attested artifacts | PyPI trusted publishing with PEP 740 attestations; cosign keyless signing of images (`.github/workflows/release.yml`, `docker.yml`) | A `.sha256` only |
| Software bill of materials | CycloneDX and SPDX SBOMs with vulnerability scans, committed in `sbom/` | None |
| Code scanning | CodeQL for Python, JavaScript and Actions, on pull requests and weekly (`security.yml`) | None |
| Secret scanning | gitleaks and GitGuardian configuration in the repository | Depends on repository settings, which are the owner's |
| Changelog | Generated by release-please from Conventional Commits, with a workflow that blocks hand edits (`changelog-guard.yml`) | None; release notes live in `docs/workflows/upgrading.md` |

### 3. Versioning, compatibility and support (P0)

Headroom doesn't publish a deprecation policy either, so this is a gap for both. Boundroom has more surface a consumer depends on: settings and their names, CLI flags and exit codes, the handoff and slice schemas, the decision report, and the sync manifest. A consumer can't tell today which of these may change in a minor release. Boundroom also lacks a written support matrix: which Python versions, operating systems and Claude Code versions are tested. CI runs Python 3.11 and 3.12 on Linux only, although the canaries ran on macOS.

### 4. Packaging and distribution (P1, owner gate)

Headroom ships wheels for five platforms, npm packages, ten container image variants and an MCP registry entry, and smoke-tests wheels before publishing. Boundroom ships a source archive, and consumers vendor it through `Tools/boundroom-sync.sh`. That model is deliberate: the consumer's copy is the authority, and a pull request records every update. Whether to also publish a PyPI package or a container image changes the distribution model, the release workflow and its permissions. That is the owner's decision.

### 5. License (P1, owner gate)

Boundroom is `GPL-2.0-only`. Many enterprises restrict copyleft licenses in internal tooling. Headroom is Apache-2.0 and runs `cargo deny check licenses` in CI. **Agents must not choose or change a license** (AGENTS.md). This spec only records the gap. The owner decides.

### 6. Telemetry and observability (P1)

| Practice | Headroom | Boundroom |
| --- | --- | --- |
| Signals | OpenTelemetry metrics (counters in `"1"` and `"USD"`, histograms in seconds), two trace spans, Prometheus `/metrics`, a local stats store (`headroom/observability/metrics.py`, `prometheus_metrics.py`) | Traces only |
| Metric catalogue | Names, units and labels kept in one constants file, with "cardinality discipline": fixed label vocabularies, unknown values mapped to `"other"` | None |
| Resource attributes | `service.name`, `service.version` from the package, operator attributes such as `deployment.environment` | Version and environment only |
| Egress control | One `guard_egress()` chokepoint and an offline switch, with a meta-test that fails when a new network path skips it (`headroom/offline.py`, `tests/test_offline_egress_chokepoint.py`) | Per-feature checks, no offline switch |
| Errors | Spans set error status; logs carry an error's type and location, never its message (`headroom/log_safety.py`) | No span status; reasons are scrubbed of the repository path |
| Operator view | `/stats` reports exporter status; `headroom telemetry` explains what is on | Settings views show the resolved values |
| Dashboards | An example Grafana dashboard (`examples/grafana/headroom-dashboard.json`) | None |
| GenAI conventions | Sets only `gen_ai.request.model`, and documents why the rest are deferred | None |

Headroom also lacks some things, which Boundroom shouldn't count as gaps: it doesn't join logs to traces, configures no sampling, writes plain-text main logs, and exports traces only to Langfuse.

### 7. Documentation for operators (P1)

Headroom's docs site has getting started, a configuration reference covering about 55 variables, observability, API reference, architecture, a security model, and errors and troubleshooting. Boundroom has the workflow guide, the generated settings reference and the upgrade guide. It lacks:

- a security model, saying what a runner can and can't do under each profile, and what leaves the machine;
- an exit-code and error reference;
- a troubleshooting guide;
- an architecture overview for someone new.

Much of this exists today only inside the specs.

### 8. Project governance (P2)

Headroom has `CONTRIBUTING.md` (with a "real behavior proof" rule for external pull requests), `CODE_OF_CONDUCT.md`, issue and pull-request templates, a devcontainer, pre-commit hooks and five ADRs on release semantics. Boundroom has `CODEOWNERS` and specs that serve as decision records. It has no contribution guide, conduct policy or templates.

### 9. Scope (P2)

Two things widen what an enterprise must review: the effectiveness benchmark (about 17 modules under `automation/benchmark/`, Hermes-specific, run only with approval), and the Hermes runner paths. Neither is needed to supervise a Claude Code or Codex runner. Packaging the benchmark separately from the supervisor would shrink the core.

Discord and Slack support is removed by the owner's decision of 2026-11-14 (raelldottin/boundroom#238), for the same reason.

## Plan

Each slice is one pull request by the agent, approved by a person, with tests where there is code.

| Slice | Gap | Change | Acceptance |

| RA-ENT-001 | 1 | Make the runner prompt generic. Move Owlory's layer rules out of `automation/prompts/base.md`. Let a consumer add its own rules from a file it owns, which the sync never overwrites. | A test fails if a shipped prompt names a consumer. Owlory's rules still reach Owlory's runners through Owlory's own file. |
| RA-ENT-002 | 1 | Remove the consumer-specific sync flag and deny rule, behind a deprecation note. | RA-ENT-006 | 2 | Keep a `CHANGELOG.md`. Each release pull request adds its section, and `release.yml` publishes that section as the release notes. | A test fails if the changelog lacks a section for the version the manifests declare. |

It says what a minor or patch release may change in settings, flags, exit codes, schemas, the decision report and the sync manifest, and how long an old name keeps working. | The policy is linked from the README and the upgrade guide, and RA-ENT-002 follows it. |
| RA-ENT-008 | 3 | Publish a support matrix. Add Python 3.13 and a macOS job to CI. | CI runs that matrix. The README states it. |
| RA-ENT-009 | 6 | Telemetry: metrics with a catalogue and bounded labels, resource attributes, span error status, safe errors, an offline switch with one egress chokepoint and its meta-test, and an operator status block. Implemented in SPEC-006 as RA-TEL-008 onward. | As listed in SPEC-006. |

| RA-ENT-012 | 8 | `CONTRIBUTING.md`, which carries the segregation-of-duties rules, plus `CODE_OF_CONDUCT.md`, issue and pull-request templates, and a pre-commit configuration that runs the same gate. *Owner gate:* the conduct policy's text. | The templates ask for the evidence the gate needs. |
| RA-ENT-013 | 9 | Package the benchmark apart from the supervisor in the sync manifest, so a consumer can leave it out. | A consumer synced without the benchmark passes its checks. |

**Order.** RA-ENT-001 and RA-ENT-002 come first, because they change what every consumer's runner is told. RA-ENT-003 to RA-ENT-008 come next and can run in parallel. RA-ENT-009 is in progress. RA-ENT-014 and RA-ENT-015 wait for the owner, and nothing else depends on them.

## What Boundroom won't copy

- **A usage beacon that is on by default.** Headroom's beacon is anonymous and documented, but it is on unless turned off. Boundroom's rule is that nothing leaves without the operator's choice.
- **Breaking 0.x releases every week.** Boundroom's consumers vendor a pinned copy through a reviewed pull request, so each minor release must say what changes and how to roll back.

## Open decisions for the owner

1. The license (RA-ENT-015).
2. Whether to publish a PyPI package or a container image (RA-ENT-014).
3. Whether the SBOM generator may be added as a tool, and whether CodeQL becomes a required check (RA-ENT-004 and RA-ENT-005).
4. Enabling secret scanning and push protection in the repository's settings, which agents never change.
5. The text of a code of conduct (RA-ENT-012).
